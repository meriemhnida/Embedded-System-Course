## Pourquoi une méthode de conception ?

Écrire du code pour allumer une LED, c'est simple. Concevoir un **système de freinage antiblocage (ABS)** pour une voiture — qui doit détecter un blocage de roue en moins de 10 ms, adapter la pression de freinage individuellement sur chaque roue, fonctionner par −40 °C comme par +85 °C, et ne jamais tomber en panne — c'est une autre histoire.

Dans votre cours, la section **Processus d'Ingénierie des SE** commence par la spécification des capteurs et actionneurs : *que doit mesurer le système ? que doit-il faire ?* C'est exactement la première phase du modèle en V.

Sans méthode structurée, les problèmes arrivent tard. **Corriger un défaut détecté en phase de validation coûte dix à cent fois plus cher** que de le détecter lors de la spécification. Dans l'industrie automobile, un rappel de véhicule peut coûter des centaines de millions d'euros.

Le **modèle en V** est la réponse de l'industrie embarquée (automobile, aéronautique, médical) à ce problème. Il organise le développement en deux branches symétriques : **concevoir à gauche, vérifier à droite**. Chaque phase de conception correspond exactement à une phase de test.

#define SLIP_THRESHOLD  0.20f
#define DEBOUNCE_CYCLES 3u

/* Calcul du taux de glissement (P2) */
float compute_slip(float v_vehicle, float v_wheel) {
    if (v_vehicle < 0.1f) return 0.0f;  /* véhicule arrêté */
    return (v_vehicle - v_wheel) / v_vehicle;
}

/* Détection avec hystérésis (P3) */
bool detect_lock(float slip, uint8_t *count) {
    if (slip > SLIP_THRESHOLD) {
        (*count)++;
    } else {
        *count = 0u;
    }
    return (*count >= DEBOUNCE_CYCLES);
}`}</code></pre>

## Les deux branches en résumé

| Phase | Branche | Question posée |
|---|---|---|
| ① Spécification système | Gauche ↘ | *Que doit faire le système ?* |
| ② Architecture système | Gauche ↘ | *Avec quels composants et protocoles ?* |
| ③ Conception détaillée | Gauche ↘ | *Comment chaque module fonctionne-t-il ?* |
| ④ Implémentation | Bas ↓ | *Comment traduire le design en code ?* |
| ⑤ Tests unitaires | Droite ↗ | *Chaque fonction est-elle correcte isolément ?* |
| ⑥ Tests d'intégration | Droite ↗ | *Les modules fonctionnent-ils ensemble ?* |
| ⑦ Validation | Droite ↗ | *Le système répond-il au besoin du client ?* |

La règle d'or : **la phase ① et la phase ⑦ sont en miroir**, tout comme ② ↔ ⑥ et ③ ↔ ⑤. Si une exigence de la phase ① n'a pas de test en phase ⑦, elle ne sera jamais vérifiée.

## Tests en boucle dans l'industrie (SIL, PIL, HIL)

L'industrie automobile et aérospatiale utilise des environnements de test progressifs pour valider le code **avant** de le tester sur le vrai matériel.

| Sigle | Nom complet | Ce que l'on exécute | Matériel cible | Équivalent dans vos projets |
|---|---|---|---|---|
| **SIL** | Software-in-the-Loop | Code source sur PC | Aucun | Tests unitaires (Unity, pytest) sur votre ordinateur |
| **PIL** | Processor-in-the-Loop | Code compilé pour la cible, sans E/S réelles | MCU cible | Programme sur Arduino, moniteur série uniquement |
| **HIL** | Hardware-in-the-Loop | Système complet avec E/S simulées en temps réel | MCU + E/S simulées | Wokwi (simulateur de matériel) |

:::note[Wokwi comme HIL simplifié]
Wokwi exécute le programme compilé instruction par instruction sur une simulation fidèle du microcontrôleur, avec des capteurs, LEDs, écrans et bus simulés. C'est une forme de HIL accessible : vous pouvez simuler un capteur défaillant, une température impossible, ou un appui long sur un bouton, sans risquer d'endommager un composant.
:::

## Diagrammes UML dans le modèle en V

L'UML (*Unified Modeling Language*) n'est pas un seul outil monolithique : chaque type de diagramme sert une phase précise du modèle en V. La règle est simple — **le diagramme suit la question posée à cette phase**.

| Phase | Diagramme UML | Rôle |
|---|---|---|
| ① Spécification | **Diagramme de cas d'utilisation** (*Use Case*) | Recense les acteurs (utilisateur, capteur, système externe) et les fonctions attendues. Répond à : *qui interagit avec quoi ?* |
| ② Architecture | **Diagramme de composants** (*Component*) | Montre les modules et leurs interfaces (capteurs, ECU, bus). Répond à : *quels blocs et comment sont-ils reliés ?* |
| ② Architecture | **Diagramme de déploiement** (*Deployment*) | Représente les nœuds matériels et leurs connexions (MCU, capteur, cloud). Adapté aux systèmes IoT multi-MCU. |
| ③ Conception détaillée | **Diagramme de classes** (*Class*) | Décrit la structure interne des modules (structs, types, relations). |
| ③ Conception détaillée | **Diagramme d'états** (*State Machine*) | Modélise les états d'un composant temps réel (ex. : ABS actif / inactif / mode dégradé). Très utilisé en embarqué. |
| ③ Conception détaillée | **Diagramme de séquence** (*Sequence*) | Montre l'ordre des échanges entre modules dans un scénario précis (ex. : séquence d'initialisation du bus CAN). |
| ⑤–⑦ Tests | **Diagramme de séquence** (*Sequence*) | Utilisé aussi pour décrire les scénarios de test (entrées, sorties attendues, chronologie). |

:::tip[Conseil pratique]
En embarqué, le **diagramme d'états** est le plus stratégique : il force à lister tous les états possibles du système — y compris les états d'erreur et les transitions inattendues. John D. Carmack l'a résumé en une phrase devenue une règle de l'industrie : *«&nbsp;A large fraction of the flaws in software development are due to programmers not fully understanding all the possible states their code may execute in.&nbsp;»*
:::

## Architectures logicielles pour systèmes embarqués

En génie logiciel classique, on parle de MVC, microservices, ou architecture en couches. Dans le monde embarqué, les contraintes sont différentes : **pas de système d'exploitation complet, RAM limitée, temps réel, absence d'allocation dynamique**. Les patterns ont donc évolué en conséquence.

### Panorama des architectures

<div style="overflow-x:auto">

| Architecture | Analogie web/SI | Description | Avantages | Limites | Cas d'usage typique |
|---|---|---|---|---|---|
| **Super-loop** (boucle principale) | Script procédural | `while(1)` : lecture capteurs → traitement → actionneurs | Extrêmement simple, prévisible | Pas de priorité, latence non garantie | Arduino débutant, prototypage rapide |
| **Event-driven** (événementiel) | MVC | Interruptions + file d'événements ; le loop traite la file | Réactif, latence faible | Complexité de la file d'événements | Interfaces utilisateur, boutons, UART |
| **HAL + couches** (layered) | Microservices | Séparation HAL / BSP / middleware / application | Portabilité, testabilité | Overhead de couches | STM32 HAL, ESP-IDF, tout code portable |
| **RTOS** | Système multi-threadé | Tâches concurrentes ordonnancées (FreeRTOS, Zephyr) | Temps réel garanti, priorités | Complexité, risque de deadlock | Systèmes critiques, IoT industriel |
| **Publish-Subscribe** | Événements/messaging (Kafka, Redis) | Modules indépendants communiquent via topics ; couplage faible | Découplage total, testabilité | Gestion de l'état global | IoT multi-MCU, systèmes distribués |

</div>

### Le pattern Publish-Subscribe en embarqué

Le pattern **Publish-Subscribe** (PubSub) est l'équivalent embarqué des architectures orientées événements du monde web. Il répond à un problème fondamental identifié dans les firmwares complexes : la **prolifération des variables globales mutables**.

**Le problème des variables globales partagées** (inspiré de Matt Liberty, Jetperch LLC) :

Quand plusieurs modules d'un firmware lisent et écrivent la même variable globale — vitesse du véhicule, état du mode, température mesurée — plusieurs problèmes apparaissent simultanément :

- **Fragilité** : un changement de nom ou de type casse tous les modules qui y accèdent directement.
- **Couplage implicite** : les modules dépendent les uns des autres sans que ça apparaisse dans les signatures de fonctions.
- **Complications de test** : il faut mettre l'état global dans la bonne configuration avant chaque test.
- **Violations de concurrence** : dans un RTOS ou avec des interruptions, deux modules peuvent lire/écrire simultanément sans protection.

**La solution PubSub** :

Au lieu que les modules partagent directement une variable, ils communiquent via un **bus de messages avec topics** :

```
       Module A                    Module B
     (Publisher)                 (Subscriber)
         │                           │
         │ publish("abs/slip", 0.3)  │
         ▼                           │
    ┌──────────┐                     │
    │  PubSub  │ ──────────────────► │ callback(slip=0.3)
    │  (bus)   │                     │
    └──────────┘
         ▲
         │ subscribe("abs/slip", cb)
         │
     Module C
  (Publisher + Subscriber)
```

Les propriétés clés du PubSub embarqué (d'après Fitterbap, bibliothèque open-source C de Jetperch LLC) :

- **Loose coupling** : les publishers ne connaissent pas les subscribers, et vice versa.
- **Retained messages** : le bus mémorise la dernière valeur publiée. Un nouveau subscriber reçoit immédiatement l'état courant à l'abonnement — plus de problème d'initialisation.
- **Topics hiérarchiques** : nommage style `abs/roue/avant_gauche/vitesse` — court (≤ 30 car. pour limiter la RAM), organisé, interrogeable.
- **Thread-safe** : les publications passent par un ring buffer pour garantir l'ordre et la réentrance dans un RTOS.
- **Pas de `free()`** : allocation dynamique à l'init, pas de libération — compatible avec les systèmes sans allocateur dynamique.

**Exemple concret : ABS multi-ECU**

Dans un véhicule moderne, l'ABS ne tourne pas sur un seul MCU. Les capteurs de roue sont sur un premier MCU, le calcul de glissement sur un second, l'affichage tableau de bord sur un troisième. Avec PubSub distribué :

```c
/* MCU 1 : capteur roue avant-gauche */
fbp_pubsub_publish(pubsub, "abs/fl/speed",
    &FBP_UNION_F32(wheel_speed), FBP_PUBSUB_SFLAG_RETAIN);

/* MCU 2 : module de calcul — reçoit automatiquement */
fbp_pubsub_subscribe(pubsub, "abs/fl/speed",
    FBP_PUBSUB_SFLAG_PUB, on_fl_speed, NULL);

/* MCU 3 : tableau de bord — s'abonne à tout l'ABS */
fbp_pubsub_subscribe(pubsub, "abs/",
    FBP_PUBSUB_SFLAG_PUB, on_abs_update, NULL);
```

Chaque MCU publie dans son propre namespace (`abs/fl/`, `abs/fr/`...). Le PubSub distribué route automatiquement les messages entre MCUs via UART ou bus CAN.

:::note[Lien avec le modèle en V]
Le choix de l'architecture logicielle se fait à la **phase ② (Architecture système)**. Il doit être justifié par les exigences de la phase ① : un système temps réel critique avec plusieurs MCUs justifie un RTOS ou un PubSub distribué ; un capteur simple sur un seul MCU peut se contenter d'une Super-loop.
:::

## Teste-toi

<Question id="c2-vmodel-q1" label="Q1">
Quelle est la différence entre un test unitaire (phase ⑤) et un test d'intégration (phase ⑥) ? Donnez un exemple concret dans le domaine des systèmes embarqués.
</Question>

<Question id="c2-vmodel-q2" label="Q2">
Dans le modèle en V, à quelle phase de conception correspond la phase de validation (⑦) ? Que se passe-t-il si un test de validation échoue ?
</Question>

<Question id="c2-vmodel-q3" label="Q3">
Pourquoi teste-t-on les valeurs exactement aux seuils (par exemple, λ = 0,20 dans l'ABS) et pas seulement des valeurs «&nbsp;normales&nbsp;» loin des seuils ?
</Question>

<details>
<summary>Voir les réponses</summary>

1. **Test unitaire** : vérification d'une seule fonction isolée, avec des entrées contrôlées. Exemple : tester la fonction `compute_slip(60.0, 55.0)` et vérifier qu'elle retourne 0,083. **Test d'intégration** : vérification que plusieurs modules fonctionnent ensemble. Exemple : vérifier que le capteur DHT22 communique avec le microcontrôleur et que la LED RVB change bien de couleur en fonction de la température lue.

2. La validation (⑦) correspond à la spécification système (①). Ce sont les mêmes exigences, vérifiées sur le système complet. Si un test de validation échoue, cela peut signifier : (a) une exigence mal écrite en ①, (b) un défaut non détecté lors des phases précédentes, ou (c) un cas non prévu. Dans tous les cas, il faut remonter au niveau correspondant pour corriger.

3. Les seuils sont les **valeurs de frontière** où le comportement change. Un `>` mal placé (au lieu de `≥`) donne un résultat incorrect exactement au seuil. Ces erreurs passent inaperçues lors des tests avec des valeurs loin des seuils. C'est la règle des **tests aux valeurs limites** : tester juste en dessous, exactement à, et juste au-dessus de chaque seuil.

</details>
